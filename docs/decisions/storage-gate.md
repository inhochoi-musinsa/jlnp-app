# 저장소 게이트 (D1, T00 ⑨)

## 상태: **BLOCKED(DEVICE, GOOGLE)** — 측정 불가, 결정 보류가 아니라 **측정 전**

- 목표(`[실무 제안]`): 시트 3,000행을 모바일 회선의 Android Chrome에서 읽는 초기 로딩이 **5초 이내**.
- 측정에는 (a) Android Chrome 실기기, (b) Google Client ID·등록된 HTTPS Origin, (c) 3,000행을 넣은 테스트 시트가 필요하다. 셋 모두 현재 없다(사용자 준비물 §11 A, D).
- **이 PC에서 측정한 값은 없다. 추정치도 기록하지 않는다.**

## 측정 절차(T07 준비물이 갖춰진 후 수행)
1. 테스트 시트에 `_JLPT_CONTENT` 3,000행(행당 payload 약 1 KB)을 채운다(앱의 팩 import 사용).
2. Android Chrome(모바일 회선)에서 앱 접속 → 로그인 → 새 기기로 간주하고 전량 읽기. `values.batchGet` 500행 단위(§4.7)로 읽고 총 시간·요청 수를 `docs/qa/storage-gate-result.md`에 기록.
3. 재방문(IndexedDB 캐시 + 증분 로딩) 시간도 함께 기록.

## 한도로 본 사전 분석(공식 한도 기준, 실측 아님)
- 읽기 한도 60회/분/사용자(`limits.md`). 3,000행 ÷ 500 = 6요청 → 한도 문제 없음.
- 3,000행 × 약 1 KB ≈ 3 MB 전송 → 응답 크기 면에서는 권장 2 MB/요청(요청 기준 권장이나 읽기 응답도 분할)보다 500행 단위가 안전.
- 지연은 회선·API 응답 시간에 좌우되므로 **[미확인]**.

## 목표 초과 시 대안(제안, 사용자 확인 필요)
기본 콘텐츠(LEARN 풀)를 GitHub Pages의 정적 JSON(`content/*.json`, `site/`에 함께 게시)으로 분리하고 시트에는 사용자 이벤트·설정·개인 추가분만 둔다. 이 경우 D1(시트 정본)의 범위가 바뀌므로 측정 결과를 본 뒤 **사용자 확인을 받는다**. 지금은 구현하지 않는다.
